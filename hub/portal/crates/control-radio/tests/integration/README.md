# `control-radio` integration stack

The CI integration stack of `plan/control/radio/lorawan.md` §10, and the acceptance test for
the standalone guarantee (decision #12, `plan/portal/monolith.md` §11.7): it runs the component
through `control-radio-harness` with **no agent subsystems started**.

```sh
cd portal/crates/control-radio/tests/integration
docker compose up -d --wait

export PROXIMOS_CONFIG=$PWD/radio.yaml
export PROXIMOS_RADIO_DATA=$(mktemp -d)
mkdir -p "$PROXIMOS_RADIO_DATA/lorawan"

# Bootstrap exactly as the Hub's chirpstack-bootstrap.service does: the two offline CLI
# subcommands, both run in-container, neither of which needs the API to be listening.
#
# 1. The only key `create-api-key` can mint offline — global admin.
docker compose exec -T chirpstack chirpstack -c /etc/chirpstack/ create-api-key \
    --name control-radio-admin
printf '%s' "<the token printed above>" > "$PROXIMOS_RADIO_DATA/lorawan/chirpstack-api-token-admin"
chmod 600 "$PROXIMOS_RADIO_DATA/lorawan/chirpstack-api-token-admin"

# 2. Replace the factory admin/admin with a seeded random password, so `admin`/`admin` never
#    exists on a listening socket (lorawan.md §4). On a Hub the value is generated by the
#    seed migration into /data/chirpstack/admin-password and applied by the bootstrap unit;
#    here it is a host file, which the harness reads through the environment override.
export PROXIMOS_CHIRPSTACK_ADMIN_PASSWORD_FILE=$PROXIMOS_RADIO_DATA/admin-password
(umask 077; LC_ALL=C tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 24 \
    > "$PROXIMOS_CHIRPSTACK_ADMIN_PASSWORD_FILE")
docker compose exec -T chirpstack sh -c \
    'umask 077; cat > /tmp/admin-password &&
     chirpstack -c /etc/chirpstack/ set-password -e admin -p /tmp/admin-password' \
    < "$PROXIMOS_CHIRPSTACK_ADMIN_PASSWORD_FILE"
```

Both subcommands are as spelled above at 4.19.0 (`--help` checked in the image, 2026-08-27):
`create-api-key -n/--name`, `set-password -e/--email -p/--password-file | --stdin`.

**That is the whole bootstrap. The tenant and read-only tokens are not minted here** — `create`
mints them itself, on the first run that finds their files absent (`lorawan/bootstrap.rs`,
`lorawan.md` §4 steps 3–4): it resolves the tenant, logs in as `admin` with the password from
`PROXIMOS_CHIRPSTACK_ADMIN_PASSWORD_FILE`, and mints `control-radio-tenant` +
`control-radio-readonly` scoped to that tenant, 0600, before it touches
`ApplicationService.Create`. A second `create` mints nothing and makes no API-key RPC at all;
deleting one token file and re-running `create` re-mints just that one, pruning its stale
ChirpStack row by name first.

> **Why `create` and not the CLI or the admin key.** ChirpStack v4's `InternalService`
> (`CreateApiKey`/`ListApiKeys`/`DeleteApiKey` — the RPCs that mint *additional* keys)
> authenticates against session claims only: an API-key bearer token is rejected there whatever
> its scope, and the offline `create-api-key` CLI mints exactly one global key and no more.
> Confirmed 2026-08-24. An earlier revision of this file bridged the gap by hand with `grpcurl`
> against `InternalService/Login`; that workaround is gone, because `login()` is now part of the
> `ChirpStack` trait and the sequence runs inside `create`. Nothing in this recipe needs
> `grpcurl` or `jq` any more.

Verified working end to end this way (all four commands below, live, real ChirpStack 4.19.0 —
not the mock client `tests/*.rs` exercise): `create` converges tenant + application + both
profiles (`gateway: "pending"`, expected with no gateway attached), a second `create` is a true
no-op with the same ids, `wipe --force` clears application/profiles/gateway while the tenant
survives (never deleted, by design), and a `create` afterward fully re-converges.

```sh
cargo run -p control-radio --bin control-radio-harness -- create --radio lorawan
cargo run -p control-radio --bin control-radio-harness -- status --json

# The live sequence, once the stack is up — driven by hand through the harness.
cargo run -p control-radio --bin control-radio-harness -- create --radio lorawan   # a no-op, stable ids
cargo run -p control-radio --bin control-radio-harness -- gateway-scan --radio lorawan
cargo run -p control-radio --bin control-radio-harness -- clear --radio lorawan --force
cargo run -p control-radio --bin control-radio-harness -- wipe  --radio lorawan --force
```

**Current ceiling of what's runnable at all without the resident agent** (decision #12,
re-checked live 2026-08-25 against both arms): `create`/`status`/`clear`/`wipe`/`gateway-scan`
all work standalone, for LoRaWAN *and* P2P (`--radio p2p` needs no ChirpStack bootstrap at all —
`create` just persists a random `net_id` locally). `node-add`, `node-remove`, `gateway-add` and
`gateway-remove` (all `--radio lorawan`) work standalone too.

`gateway-add`/`gateway-remove` are **routed, not 34** — an earlier version of this paragraph
listed `gateway-add` among the `Phase2NotImplemented` commands, which was wrong.
`gateway-add` is gated on an opt-in instead: without `PROXIMOS_GATEWAY_BRIDGE_ENABLED=1` it
returns `BridgeDisabled` (exit **30**, `component: chirpstack-service`), because with the
gateway-bridge off port 1700 never opens and a registered external gateway could never connect.
With the flag set it registers.

Still `Phase2NotImplemented` (exit 34), by design — these need state only the resident
`proximos-control` agent will own, and this binary deliberately starts no agent subsystems:
`node-list`, `node-get`, `node-info`, `node-send`, `gateway-list`, `gateway-info`,
`node-scan-start`/`-stop`, and `node-add --radio p2p` (needs the node registry). `node-add
--radio p2p` still validates its registration bundle locally first, so a partial bundle is
`InvalidArgument` (exit 2) rather than 34 — the refusal names the side that is actually missing.

> `node-remove` publishes the empty retained tombstone on
> `proximos/{hostname}/nodes/{dev_eui}/info` that `plan.md` §9.4 requires — five levels, not
> six: `transport` rides inside the document since #73. On the P2P arm without a live session
> the publish is mandatory, since the runtime's detach path never runs for such a node, so the
> command refuses with `ServiceDown` when no broker is reachable rather than deregistering a
> node whose retained document nobody can then clear.

### `node-add --radio lorawan` — wired and working against a stock bootstrap

Live-verified 2026-08-25, with the tenant/admin tokens exactly as this README's own recipe
mints them — **no workaround, nothing swapped**: first enrollment, an idempotent re-add that
rotates the AppKey (confirmed server-side via a raw `GetKeys`, not just the reported flag), the
dev_eui-collision refusal, the `--otaa`/`--abp` usage error, and a full `create` → `node-add` →
`clear` → `create` → `node-add` round trip all match `plan.md` §5's documented envelope and
error shapes exactly.

```sh
cargo run -p control-radio --bin control-radio-harness -- node-add --radio lorawan \
    --profile default --serial TEST-SN-0001 --dev-eui 0011223344556677 --otaa \
    --keys-file <(echo '{"app_key":"00112233445566778899aabbccddeeff"}')
```

**Root cause of the earlier `Unauthenticated` blocker, found and fixed 2026-08-25**: ChirpStack
authorizes a tenant key for `DeviceService.Get`/`Delete` with an `EXISTS` join against the
device row itself (`chirpstack/src/api/auth/validator.rs`'s `ValidateDeviceAccess::validate_key`,
`Flag::Read`/`Flag::Delete`) — for a `dev_eui` that does not exist yet (exactly `Enroller::
enroll`'s ask-first check before every `create_device`, and exactly what `Enroller::remove` sees
for an already-gone device) that join matches zero rows and ChirpStack returns
`Unauthenticated`, never `NotFound`. Confirmed with a raw multi-token gRPC probe: a tenant token
can `Get`/`Delete` a device that already exists, and can `Create` a brand-new one (that RPC is
scoped by `application_id`, which is always real), but cannot `Get`/`Delete` a `dev_eui` that
isn't there — only the admin key's `is_admin` branch skips the join. **Fix**: `get_device` and
`delete_device` in `tonic_client.rs` now use `Scope::Admin`; every other `DeviceService` call
stays on `Scope::Tenant` since by the time `enroll.rs` reaches them the device row already
exists. See `token.rs`'s module doc and the inline comments on both calls for the full citation.

Remaining work, roughly in order:
1. ~~`node-remove` (LoRaWAN)~~ — wired 2026-08-25 and verified against the bench device;
   `gateway-remove` went in with it.
2. P2P's `node-add` registration bundle (`--serial`/`--dev-eui`/`--keys-file`, all three
   required, `plan.md` §5) — the pairing-window loop it used to wait on is gone (`p2p.md` §8,
   2026-08-27), so what remains is the node-registry write itself (`p2p.md` §7, issue #21):
   agent-owned state, still not just a wiring gap like the LoRaWAN arm was. The argument
   validation is already wired here.
3. There is still **no fPort-85 codec in this crate**. `decode::command` is policy guards, the
   seq allocator and the page reassembler; `decode::decode_uplink` returns `None` for any
   fPort other than 2 or 3. Downlink commands can only be exercised by hand through
   `DeviceService.Enqueue` with bytes built by the firmware's own `ttn.js encodeDownlink` —
   which is how the wire contract below was checked.

> **There is no automated live suite yet.** An earlier version of this file gave the recipe as
> `cargo test -p control-radio --test live -- --ignored`; `tests/live.rs` does not exist, so that
> command does nothing. The stack is driven by hand through `control-radio-harness`, and the
> acceptance list below is the **target** for that suite, not a description of current coverage.

## Live bench: a real ProXimos Node over an external gateway, 2026-08-25

The stack above was driven against real hardware rather than a fake, to answer one question:
do the CLI commands actually reach a Node?

**Topology** — nothing was written to the gateway or to the v1 Hub:

```
ProXimos Node (fw v1.4.0, DevEUI 58760700c0668fc7)
  └─ LoRa ─> Milesight UG63 gateway (EUI 24e124fffefd3bda, Semtech UDP)
       └─> v1 Hub's chirpstack-gateway-bridge ─> the Hub's mosquitto (loopback)
            └─ ssh -L tunnel ─> mosquitto bridge in this compose stack
                 └─> ChirpStack 4.19.0 here
```

Two bootstrap deltas worth knowing before repeating it:

- **A host `mosquitto` may already own port 1883.** The compose broker then fails to bind, and
  the crate's hard-coded `127.0.0.1:1883` reaches the *host* broker rather than this one. The
  bench published the compose broker on `127.0.0.1:11883` instead and seeded the host broker's
  retained `eu868/gateway/{eui}/state/conn` topic, which is what `gateway-scan` and `create`
  read for discovery.
- The Node's LoRaWAN root key was rotated before the run, so the v1 Hub's join-MIC check fails
  and only this stack answers it. Both Hubs still hear every frame.

**What went end to end.** `create` (tenant → application → device profiles → gateway
registration from the discovered EUI) → `node-add --radio lorawan` → the Node's OTAA join over
the air → `event/join` → the firmware's autonomous fPort-85 GetInfo right after joining → fPort-2
telemetry. The crate's `decode::decode_uplink("node", 2, …)` output on a live frame is
**field-for-field identical** to the firmware's own `ttn.js` decoder — 15 fields, byte-identical
input, no differences. `node-remove` → `create` → `node-add` → rejoin also completes.

**fPort-85 downlink contract**, exercised by hand through `DeviceService.Enqueue` with payloads
from `ttn.js encodeDownlink` (raw protobuf, **no** `0x01` version byte — only uplinks carry it):

| Command | Sent | Answer |
|---|---|---|
| `get_info` seq 7 | `08072200` | `DownlinkResponse{seq: 7, info{…}}` — fw 1.4.0, serial, uptime, battery, `device_status 0` |
| `get_config` page 0 / page 1 | `08082a00` / `08092a020801` | `config_dump{page_count: 6}`, lorawan group then the rest |
| `set_param` `interval_report` | — | `ack`, confirmed by the device shell |
| `clock_sync` seq 11 | `080b6200` | delivered; answered by a deferred `Info` uplink carrying `unix_time`, not an immediate `ack` |
| `w1_scan` seq 12 | `080c7200` | `error{code: 3, detail: "1-wire bus"}` — a valid answer; no 1-Wire probe is attached |
| `force_send` seq 14 | `080e4a00` | an extra fPort-2 telemetry uplink, which is the response |
| **`device_reset` seq 13** | `080d4200` | **`error{code: 3, detail: "transport not allowed"}`** |

That last row is a **contract defect, not a device fault**. `app/src/app_config.yml` at tag
`v1.4.0` declares `device_reset` (proto_id 8) `transports: [nfc, shell]`, so the firmware's
dispatcher refuses it over the radio. `plan.md` §5 and `node-firmware-v1.4.0.md` §6 row 8 both
still list it as radio-allowed; those two rows are the radio plan's to amend. This crate now
treats it as `NfcOnly` and gives it no CLI spelling.

**Duty cycle bounds the pace.** At DR0/SF12 the EU868 1 % budget is exhausted after a handful of
forced uplinks; the firmware then logs `LoRaWAN Send failed: Duty-cycle restricted` (-111) and no
RX window opens, so a queued downlink looks like a non-response. Leave several minutes between
downlink tests, and check `GetQueue` has drained before concluding anything from silence.

**Failure paths, re-checked live**: a stopped ChirpStack → `status` exits **0** reporting
`api_status: "unreachable"` with token presence intact (it used to exit 20 and drop the whole
block), while `create` gives 20. A *paused* ChirpStack — TCP up, no answers — gives
`Timeout` (21) in ~25 s; before the client-side deadlines it blocked indefinitely. Absent token
→ 10 `token-file`; corrupt tenant token → 11; unreadable `nodes.json` → 40 `enrollment-record`;
malformed `config.json` → 40 `config-json`. Discovery, which measured 5.18 s, is 0.56 s.

**One unfixed finding.** Two `create` runs racing on a fresh tenant leave **duplicate**
applications and device profiles: one arm exits 22, the other 0, and the next `create` then
reports `converged` all true with an empty `drift` while ChirpStack holds two of everything.
`wipe` cannot clean it up either — it deletes only the ids `config.json` recorded, so the
orphans survive and have to be removed out of band. The boot path is a single oneshot so this
needs concurrent invocations to hit, but the ask-first upsert has no lock and `drift` does not
notice the duplicates.

## What the live suite is meant to cover

**Target** (`lorawan.md` §10): the three-token bootstrap with all three files landing at the right scope; `create`
converging and then being a no-op with stable ids; OTAA enrollment and the re-add key rotation;
ABP refused locally before any RPC; `clear` then `wipe` with the tenant surviving; and the
failure paths — a rejected token as `Unauthenticated` (exit 11, not retryable), an absent token
file as `NotBootstrapped` (exit 10), a stopped container as `ServiceDown` (exit 20, retryable).

**Does not cover**: SQLite-specific bootstrap behaviour. Upstream publishes no SQLite container,
so this runs the PostgreSQL build while the device runs the SQLite one. Their duplicate-key
error messages differ — which is precisely why converge asks before creating rather than parsing
error text, so the gap is bounded by design rather than by luck.

**Does not cover**: anything P2P on real hardware. The northbridge firmware is issue #20 and the
bench unit's BOOT0 problem is issue #37. The Hub side is exercised by unit tests over inline
byte arrays — there is no simulated-modem fixture, despite what `p2p/mod.rs`'s doc comment says,
and no production code builds or parses a JoinRequest/JoinAccept frame yet: those layouts live
in doc comments and `#[cfg(test)]` helpers. `p2p::uart`'s read loop is tested against
`AsyncRead`; opening a real port is not.
